# Bosun during normal Slipway updates

The existing Update button, Docker installer and `slipway-bosun` sidecar remain the update path. Required Slipway SQLite changes run through the same migration executor as Bosun Migrate, inside the candidate image, before Sails lifts. Customer application databases and PostgreSQL services are outside this release registry.

Published 0.0.87 starts `slipway-next` against the live database mounts while the old web server still runs. That container only validates copies and serves preflight health. It never lifts Sails or writes live schema. The existing sidecar stops the old container before starting the candidate normally. Normal startup checks for other running Docker containers with overlapping writable storage, validates all pending datastore plans on copies, then applies each datastore in its own SQLite transaction.

Each transaction records its release checksum and verified backup together with its schema changes. A process killed before commit rolls back both. Normal startup lets SQLite recover a hot rollback journal left by a killed transaction before reading receipts; clone-only preflight remains read-only and rejects that interrupted state. A restart recognizes committed receipts, verifies the required schema and resumes remaining datastores. SQLite locks and immutable schema checks reject competing migrations; secondary production helpers verify receipts instead of creating tables. Development and test initialization remain available. Team membership, encrypted configuration, Bearing data normalization, service recovery and telemetry timestamp backfills remain in their existing helpers.

The fixed registry covers fresh storage, published 86/87 native schemas, and partial or complete manual Bosun adoption. Unknown owned definitions, altered checksums, missing populated datastore files, aliases and competing Docker writers block startup for review. Unrelated custom native tables, indexes, views and triggers remain intact. No down-migration or automatic database snapshot overwrite is performed. Because these release changes are additive, restarting the old server after a failed candidate preserves any committed changes; it does not reverse them.

## Recovery and limits

The four owned files are `app.db`, `observability.db`, `analytics.db` and `stash.db`. Every affected datastore gets a private SQLite backup, verified for integrity, native schema, all table row counts and SHA-256. Backups under `db/migration-backups` are retained automatically, including after partial failure. Receipts retain their paths and hashes. Operators can remove obsolete snapshots after independently validating the completed installation and their recovery policy; the updater does not silently delete recovery data.

Preflight checks free space on the live and temporary filesystems before changing live databases. It reserves conservative headroom of three times the existing datastore size plus 32 MiB, covering validation copies, their verification backups and retained live backups. Receipt-only restarts need no new snapshots. Validation and migration have a 45-second cooperative deadline checked between phases, during SQLite backup chunks and immediately before commit. SQLite lock waits are bounded at five seconds. Native SQLite integrity checks and individual SQL calls are synchronous; the deadline does not interrupt a running native call. The released 87 sidecar retains its original health window, so the actual-image CI proof also verifies first-upgrade timing separately.

Normal `/health` verifies registered schema receipts before returning readiness. New swap scripts also require the registered migration version and checksum, and reject preflight-only health. Release package metadata is prepared separately from the registry; this change alone does not publish 0.0.88.

## Evidence and scope

CI exercises the actual published 87 image's unchanged validation and Bosun swap control flow, verifies founder/auth and custom data, validates retained backups and receipts, and boots a fresh production volume. The fixture records its limited substitutions for unreleased candidate acquisition, release discovery, optional remote backup, progress cache and port allocation.

Native tests cover transaction interruption with owned SIGKILL processes, partial resume, receipt drift, unknown schemas, byte-identical repeat startup, manual adoption, storage aliases, capacity/deadline failures, production helper DDL retirement and failed swap ordering. Three fixed small and 64 MiB payload samples report preflight, live apply and total durations, source/backup size and additional owned file bytes sampled at completed clone/transaction checkpoints. Those checkpoint metrics do not include transient journal peaks or live-file growth. A separate verification fixture continuously polls the owned live/temporary trees from an independent process at a requested 2 ms interval and records the actual largest sampling gap. It reports additional logical bytes and filesystem-reported allocated bytes (stat.blocks × 512), separating journals, live-file growth, clones and backups. Each real live transaction is held for 100 ms by a test-only precommit pause so short-lived journals are observable; these instrumented elapsed times are not migration performance measurements. Aggregate peaks come from individual scans; category maxima can occur at different times and must not be summed. Polling can miss changes between scans and does not measure the physical device peak. These are measured fixture distributions, not a production performance guarantee or a measurement of peak physical filesystem allocation. The live-apply duration bounds the database writer transaction work within the candidate's startup downtime; Docker swap and Sails lift are measured separately by the actual-image proof.

The normal updater does not require a separate native host archive, host Node/glibc selection, a new daemon, a new migration CLI/coordinator UI, global host process discovery or customer storage-engine upgrades. Requirements tied to that rejected host-bundle design are superseded by this container handoff. The existing authenticated update action owns initiation; per-datastore transactional receipts and Docker writer checks provide bounded recovery. Production upgrades and releases remain separate, explicitly coordinated operations.

The verification fixtures also hold a real SQLite writer lock in another owned process and prove the five-second admission wait fails without live changes, then succeeds after release. Native backup faults interrupt after copied pages or corrupt the completed copy before verification; both refuse DDL, remove the incomplete snapshot and preserve live bytes. Native COMMIT faults model a lost result before and after the real commit; restart reconciles the durable schema/receipt, retains already committed receipts and applies only remaining datastores. Fault adapters exist only in the isolated tests, and production guards are unchanged.
